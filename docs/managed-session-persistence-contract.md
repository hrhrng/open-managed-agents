# Managed Session persistence: documented semantics vs OpenMA implementation

This note is about the **official `/v1/sessions` Managed Agents path**. The legacy `/v1/oma/sessions` and `S3MemoryPoller` are separate code paths; do not use their behavior to certify this path.

**Do not conflate three filesystems:** an attached *memory store* is canonical API data exposed under `/mnt/memory/<store>/`; the sandbox *working directory* (`/workspace`) is per-session runtime state whose retention depends on the sandbox/provider; *outputs* are selected deliverables, not an automatic copy of the whole working directory. Anthropic also uses “workspace” for an organization/account scope; that is not the `/workspace` filesystem. OpenMA's internal `.openma-managed-memory-workspaces/` prefix names a writable **memory-store staging snapshot**, not the sandbox working directory. Neither the official memory sync nor OpenMA's memory reconciliation promises to persist arbitrary `/workspace` files.

## Anthropic's published contract

- [Using agent memory — How the agent accesses memory](https://platform.claude.com/docs/en/managed-agents/memory#how-the-agent-accesses-memory): a memory store is presented under `/mnt/memory/<name>/`; writes to a read-write store persist and are shared across sessions. For **self-hosted** sandboxes it is a *local copy*, not a live remote mount. The SDK worker reconciles after tool calls, at most once per sync interval (15 seconds by default), and on session end. A change becomes visible to another running self-hosted session after **both workers** sync.
- [Self-hosted sandboxes — How the worker handles memory](https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes#how-the-worker-handles-memory): `EnvironmentWorker` downloads attached stores, synchronizes local and remote edits, uploads pending changes on graceful cancellation/session end, and cleans up local directories. Hard-killed workers can lose unsynced local edits. [Configure sync](https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes#configure-sync) documents the interval and deletion policy (enabled by default).
- [Attach and download files](https://platform.claude.com/docs/en/managed-agents/files): on **Anthropic-hosted** sandboxes, files under `/mnt/session/outputs/` appear in the Files API shortly after writing, possibly a few seconds **after** `session.status_idle`. Idle alone is not proof that upload completed. [Self-hosted sandbox filesystem](https://platform.claude.com/docs/en/managed-agents/self-hosted-sandboxes#sandbox-filesystem) instead places deliverables in the user's sandbox filesystem, typically `/workspace`; it does **not** promise automatic `/mnt/session/outputs` uploads there.
- [E2B's Claude Managed Agents JavaScript example](https://github.com/e2b-dev/e2b-cookbook/tree/1952c800623ef78198e36136ba8133c7f174fb24/examples/anthropic-managed-agents/javascript) runs Anthropic's SDK `EnvironmentWorker` **inside** an E2B sandbox (`src/worker-runtime.ts`, `workdir: /mnt/session`). It reconnects by sandbox ID and creates sandboxes with `lifecycle: { onTimeout: "pause", autoResume: true }` (`src/sandbox-worker.ts`), so the **same E2B sandbox** retains `/mnt/session` across idle/pause and follow-up work. The webhook examples default to one sandbox per session; the direct orchestrator can reuse one sandbox across sessions. Memory under `/mnt/memory` is downloaded/reconciled by Anthropic's SDK worker, not by an E2B FUSE/OSS mount. `/mnt/session/outputs` is a *suggested sandbox-local artifact directory*, not automatically the Anthropic Files API or a shared OSS output store. The example's JSON session-to-sandbox assignment store explicitly requires replacement with transactional storage for multi-instance deployments. See also [provider adapter audit](claude-managed-agents-sandbox-provider-audit.md). This reference targets Anthropic Environment Work and is not automatically plug-compatible with OpenMA's embedded adapter.

## Two OpenMA runtime compositions (do not conflate them)

The following bullets describe the **main-node embedded `nodeDefaults` path selected by mmopenma**, not every OpenMA runtime. The separate [managed-runtime persistence architecture](../apps/docs/src/content/docs/self-host/sandbox-persistence.mdx) already defines `WorkspacePersistencePort` with `durable_mount` / `retained_runtime` / `checkpoint_restore` / `ephemeral`, `SessionOutputPort` with `final_collect`, and separate Memory Store synchronization. Its E2B preset (`packages/managed-runtime-e2b/src/e2b.ts`) advertises provider snapshots for portable workspace restore and S3-backed output collection when configured. Those ports are not installed merely by injecting `createE2BSandbox` into `nodeDefaults`.

- `apps/main-node/src/lib/node-managed-session-inputs.ts` materializes memory snapshots and invokes `mountMemoryStore`, and invokes `mountSessionOutputs` for every managed session.
- `apps/main-node/src/lib/node-managed-session-runner.ts` calls `synchronizeSandbox` at **turn finalization before** emitting `session.status_idle`; it does not perform the Anthropic SDK worker's after-tool-call 15-second reconciliation. The synchronization hook in `apps/main-node/src/modules/node-managed.ts` reconciles writable **memory-store staging snapshots** through a fenced canonical API, then collects outputs. It does not collect or sync the general sandbox `/workspace`.
- `apps/main-node/src/lib/node-managed-session-outputs.ts` has a `best_effort` collector but currently stages outputs in a node-local `outputsRoot`; it is not a cross-replica durable sink. The existing E2B adapter instead advertises a `durable` mount if bucket configuration is present. Changing its capability label is not a persistence implementation.
- `apps/main-node/src/lib/s3-memory-poller.ts` indexes the **legacy** memory repository and is not the official Managed Session workspace synchronizer.

## Acceptance needed before a multi-replica claim

Prove with two independent control-plane processes and a shared SQL/object store: A writes memory and outputs, B reads them after the documented synchronization boundary; a stopped A cannot erase B's result; stale execution attempts fail the fence; deletion/conflicts are reconciled. For self-hosted-like semantics, separately test visibility **during a long turn** after the configured sync interval, and graceful cancellation/unsynced hard kill. For outputs, test readback after the writer process is gone, not merely existence under its local filesystem. Provider adapter tests do not replace these core tests.

These are external semantics and observations about the selected composition, **not a claim that the existing managed-runtime ports are absent or that mmopenma has installed and certified them**.
